# ILAS S-4 Wire Specification (draft for review)

**S-4** is ILAS's name for its anchoring layer: the clerk seam (§7), the head
commits (§3), the witness receipts (§4) and the continuity check (§6).
Together they let a party outside the node show that the node's evidence log
(L0, §5) was not cut back or rewritten. The name appears in file names
(`docs/S4-WIRE-SPEC.md`, `docs/s4-test-vectors.json`, `src/s4/`) and means
only this layer.

Status: **draft, not shipped.** Describes what the code in this repository does.
Where the code does not yet do what a reader would expect, the gap is listed in
§7.4.

Test vectors: `docs/s4-test-vectors.json`, generated by
`scripts/s4-test-vectors.ts`. Re-run the generator and check that the file is
unchanged (§8). The vector keys are **public test seeds**: 32 bytes of `0x42`
for the witness key, and a separate 32 bytes of `0x43` for the clerk key. Never
use either for a real deployment.

---

## 1. Roles

| Role | What it does | Where it runs |
|---|---|---|
| **ILAS (L0)** | Keeps a hash-chained append-only log. Emits HEAD_COMMIT records. Verifies clerk receipts (§7.3) and continuity (§6); its witness client verifies witness receipts (§2, §4.1). | The node. |
| **Clerk** | Sequences, timestamps and signs each entry before L0 commits it. Returns a signed submission receipt (§7). | A separate process. Operator chooses where. |
| **Witness** | Retains the head hashes it is sent. Signs a receipt for each one (§4). | A separate process, ideally a separate operator. |
| **Deployer** | Decides who runs the clerk and witness, and where keys are held. Declares that choice (§2). | Human. |

ILAS never imports a clerk or witness implementation. It talks to them only
through the messages in §3, §4 and §7 and the public keys it has been
configured with.

**Reference implementations.** This repository ships one clerk and one witness,
each written from this spec and each with its own README:

| Package | What it is | Wire |
|---|---|---|
| `packages/clerk` | A clerk daemon (clerkd) behind a Unix domain socket, and two clients that satisfy L0's `ClerkSubmitClient` | §7, §7.5 |
| `packages/witness` | A standalone witness process with its own hash-chained store | §3, §4, §4.1 |

The packages may import ILAS's wire helpers (for example the canonical form in
`src/l0/canonical.ts`). ILAS core never imports them. `package.json` declares
no runtime dependencies: its only dependencies are the development toolchain
(`typescript`, `ts-node`, `@types/node`), as `devDependencies`.

**The packages run from a copy of this repository.** They have no
`package.json` of their own. They import ILAS's canonical form and its key
fingerprint helper (and the clerk also L0's types and its receipt check,
`verifyClerkReceipt`, for `reconcile`) by relative path, their command lines
run through `ts-node`, and `npm run build` compiles only `src/`. So every
machine and account that runs one needs a checkout of the same commit with
the `devDependencies` installed (`npm install`, not `npm install
--omit=dev`). The reference clerk speaks only over a Unix domain socket, so it
runs on the node's host (under a separate account, if the deployment wants
one). The reference witness speaks through directories; a witness on another
machine needs a directory both machines reach, which the deployer provides
(G10, §7.4).

`src/fence.test.ts` is a static check that stops **accidental** dependencies:
an import added without noticing where it leads, a helper copied in with its
`require()`. It reads the source and does not run it. It is not a sandbox
against deliberate evasion; code written to hide a load from it can do so (see
below), and reviewing changes is the defence against that. Its rules:

- Every file under `src/` must be a `.ts` file (its name ends in `.ts`, lower
  case). Anything else is refused unread: `.js`, `.json`, `.mts`, `.TS`, a
  file with no extension, a `.node` addon, and a `package.json`, whose `main`
  could send a directory import outside `src/`. A symbolic link under `src/`
  is refused, and so is a file that does not parse. Each `.ts` file is parsed
  with the TypeScript compiler and its syntax tree is walked.
- Every module reference counts: `import` and `export … from` declarations
  (type-only ones included), `import x = require(…)`, type-level and dynamic
  `import()`, `require()` however it is spelled or called (optionally,
  parenthesised, or as a member named `require`), `require.resolve()`, and
  triple-slash path references.
- The specifier must be one string literal, or a template literal with no
  substitution, and is judged by its text with escapes resolved. A computed
  specifier (a concatenation, a variable, a substitution) is refused.
- A relative specifier must resolve inside `src/`. An absolute one is refused,
  even inside `src/`. A bare one must name a Node built-in module (a `node:`
  prefix is allowed). Runtime files (every file except `*.test.ts`, fixtures
  included) may import nothing else, and may not name the `module` built-in,
  which is Node's loader. A test file may also import the `devDependencies`;
  the fence itself imports `typescript`.
- `require` used other than by a direct call (kept in a variable, passed
  along, destructured under another name, or named by `import x =
  require.cache`) is refused. `require.main` is allowed in test files only.
  Node's loader internals are refused by name, in every file: `createRequire`,
  `_load`, `_resolveFilename`, `_compile`, `_extensions`, `dlopen`,
  `mainModule` and `getBuiltinModule`.
- In a runtime file the `module` object may be used only as `module.exports`
  (or `typeof module`): `module.require`, `module.constructor` and
  `module.parent` are refused. `arguments` outside an ordinary function is
  refused in every file: at the top level it is the CommonJS wrapper's, which
  holds `require` and `module`.
- Comments and the contents of strings are not code and are not checked.

What the fence cannot see: a name built at run time (`m["_lo" + "ad"]`, or one
passed to `Reflect.get`), `eval`, `new Function`, the `vm` module, and a module
loaded by a child process or a worker thread. Test files are held to less:
they may use `require.main`, the `module` object and the `module` built-in.
`tsc` (with `rootDir` `src`) is the second check for static imports. Using the
packages is optional; any implementation of this wire will do. Running one
does not make it independent (§2).

## 2. Independence is a deployment fact

Code cannot verify that a witness or a clerk is independent. What it can do is
refuse to treat an unverified or unconfigured witness or clerk as evidence.

What ILAS checks:

- **Witness receipts are checked by the `Witness` implementation, not by the
  continuity predicate.** `ContinuityVerifier` (§6) checks every receipt the
  configured `Witness` returns against the live chain. It does not check a
  receipt's signature or shape: it takes what the `Witness` returns.
- ILAS's own `FileDropWitness` (§4.1) does that check. Its witness public key
  **must be configured explicitly**; there is no default, and a file holding a
  private key is refused. It returns a receipt only if the receipt has exactly
  the shape of §4 and its signature, in canonical base64, verifies against that
  key. A receipt it was able to check and refused is reported, and continuity
  then reads `REJECTED_RECEIPTS` (§6).
- **A custom `Witness`** (for example over another transport) must do the same
  before it returns a receipt: check the exact shape of §4 and verify the
  signature against a configured witness public key, and report what it
  refused through `retrievalIssues()` (§6). A `Witness` that returns receipts
  unchecked lets an unsigned or forged receipt count as reproduced; ILAS cannot
  tell.
- If no key is configured, or no receipt verifies and none was refused, the
  continuity status is `CANNOT_VERIFY_CONTINUITY`.
- A clerk route's public key must also be configured explicitly, and must be a
  public key: a private key is refused. It is checked when the log is built.
  Every clerk receipt must verify against it, name the route's `submitterId`
  and `channel`, and stand on the log at most once (§7.3). With a durable log,
  every receipt is checked again when the log is loaded (§7.3).

What ILAS does **not** check, and only records as a declaration:

- Which machine, account, or operator runs the witness or the clerk.
- Where the witness key and the clerk key are held.
- Whether the witness keeps its store append-only, or the clerk its book.

Declarations are recorded as text and reported as claims, never as verified
facts. Shared-account deployments are allowed, but they are **self-witnessed**
(and the clerk **self-operated**), and the declaration should say so.

### 2.1 Declarations

`ILASKillStack` takes the deployer's declarations as an option:

```
new ILASKillStack({ ..., declarations: { witness?: string, clerk?: string } })
```

`status().declarations` reports them as:

```
{
  witness: string | null,
  clerk: string | null,
  verified: false,
  warnings: string[],
  keys: { clerk: string | null, witness: string | null }
}
```

- `verified` is always `false`. A declaration is a claim; nothing in ILAS
  checks it.
- A declaration that was not given is reported as `null`. So is one that
  states nothing: a value that is not a string, or a string that is empty or
  only whitespace (`text.trim()` is empty). Such a declaration also counts as
  not given in `warnings`. Any other string is reported exactly as given,
  surrounding spaces included.
- The strings are copied at construction. Changing the options object later
  does not change what `status()` reports. Each `status()` call returns a new
  object.
- Declarations never change the continuity reading or the V0 state.
- `warnings` lists, in plain sentences, the contradictions ILAS can see
  between the declarations and its own configuration. It is built from the
  configuration only; the declaration strings are not parsed. There are four:
  - `A witness is declared, but no witness is configured (NullWitness): nothing outside this node holds its heads.`
  - `A witness is configured, but no witness declaration was given: who operates it is not stated.`
  - `A clerk is declared, but this node has no clerk route: no entry is stamped by a clerk.`
  - `A clerk route is configured, but no clerk declaration was given: who operates the clerk is not stated.`

  An empty list does not make a declaration true: it only means none of these
  four contradictions is visible.
- `keys` names the keys the node was given, as fingerprints: `"sha256:"`
  followed by the lowercase hex SHA-256 of the key's SPKI DER bytes
  (`publicKeyFingerprint()`, exported from `src/index.ts`). `keys.clerk` is the
  clerk route's key (also `LockedEvidenceLog.getClerkKeyFingerprint()`), `null`
  without a route. `keys.witness` comes from the
  witness's optional `publicKeyFingerprint()` method (§6), read at every
  `status()` call; it is `null` when the witness has no such method, has no
  usable key, or the method throws or returns something that is not a string.
  Both packages' `keygen` and `fingerprint --pub <pem>` commands print the
  same format, so each operator can confirm out of band that the node holds
  their public key. A matching fingerprint shows which key the node trusts,
  not who holds its private half.

Recommended labels:

| Label | Use it when |
|---|---|
| `self-witnessed` | The witness runs under the node operator's control: the same person, possibly the same account. |
| `self-operated` | The clerk runs under the node operator's control. |
| `independent-operator: <role>` | Someone else runs it. `<role>` names them, for example `independent-operator: security department`. |

ILAS does not parse these strings. They are recommended so that a reader of
`status()` can tell the cases apart.

### 2.2 Deployment guidance

| Deployment | Who runs the witness and the clerk | Who holds their private keys | Declared labels |
|---|---|---|---|
| Private, one person | That person. They may run under the same account as the node. | That person | witness `self-witnessed`, clerk `self-operated` |
| Enterprise | A superior or a designated department, on a separate host or under a separate account | That operator. The node's operator receives only the public keys. | `independent-operator: <role>` |

- **Private, single person.** Running the witness and the clerk under the same
  account as the node is allowed, but it must be declared. It still catches
  accidents and a chain rebuilt later by mistake, and the clerk's book still
  records what was submitted, in what order and when. It does not stand against
  that account's operator: the account that can rewrite the chain can also
  rewrite the witness's store and read the clerk's key.
- **Enterprise.** A superior or a designated department runs the witness and
  the clerk, on a separate host or under a separate account, and holds their
  private keys. The node's operator receives only `witness.pub.pem` and
  `clerk.pub.pem`, and confirms with that operator, out of band, that their
  fingerprints match (§2.1, `keys`).
- **What the reference packages support.** A separate account on the node's
  host, for both. The reference clerk cannot run on another host: it speaks
  only over a Unix domain socket. The reference witness can run on another
  host only if the deployer provides a directory both hosts reach (shared or
  synced) for the intake and the outbox, and works out who can write what on
  it. No transport between machines is included or tested (G10). Creating the
  operator's account, its group and the shared directories needs an
  administrator; it is not something the packages, or an agent installing
  them, do.

**Installing with an AI coding agent.** An AI coding agent may help a
non-expert install ILAS, following `docs/INSTALL-FOR-AGENTS.md`. The agent must
not choose the operator. Who runs the witness and the clerk, on which machine
or account, and who holds their keys are questions the agent asks and the human
answers.

## 3. HEAD_COMMIT (local, decorative)

Emitted by `emitStartupCommit()` once after start-up, and by `emitHeadCommit()`
on a cadence the deployment drives. Submitted to the witness.

```
HeadCommit {
  seq_no:         number   // sequence of the head at emit time; -1 if empty chain
  head_hash:      string   // hash of that head; GENESIS (64 zeros) if empty chain
  ts:             number   // local emit time, ms
  witness_set_id: string   // witness set this head was sent to
}
```

A HEAD_COMMIT is bookkeeping, not evidence. Nothing verifies against it. Its
purpose is to record what was sent to the witness.

**Empty chain.** A chain with no entries emits `seq_no: -1` with `head_hash`
set to the genesis hash, 64 zeros (the genesis `previousHash` of §5). Seq −1
is the head of the empty prefix, which every chain has, so a receipt for −1
with the genesis hash reproduces on any chain, empty or not (§6). The emitter
pairs the genesis hash only with −1. The reference witness refuses a commit
that pairs −1 with any other hash, or the genesis hash with any other `seq_no`
(§4.1).

## 4. WITNESS_RECEIPT (signed by the witness)

```
WitnessReceipt {
  seq_no:     number
  head_hash:  string
  witness_ts: number       // witness's time, ms
  witness_sig: string      // base64 Ed25519 signature over the preimage
}
```

**Preimage** (exact):

```
preimage = [ String(seq_no), head_hash, String(witness_ts) ].join(" ")
```

Example (from the vectors):

```
3 9da9efa8574d56d89680217063fc4732374b9a5a6032caeaa7367a62a3b49cc8 1700000000123
```

The signature is Ed25519 over the UTF-8 bytes of the preimage, base64-encoded.

**Signature encoding:** `witness_sig` is the canonical base64 of the 64-byte
signature: standard alphabet, `==` padding included, 88 characters, so that
`Buffer.from(s, "base64").toString("base64") === s`. Verifiers reject any other
spelling (padding left off, URL-safe letters, whitespace, characters appended,
the unused bits of the last character set), even where a lenient decoder would
read the same 64 bytes. Both `FileDropWitness` and the reference witness's own
verifier apply this rule.

**Shape rule:** a receipt object must have exactly the four keys above. Any extra
key makes it invalid. The signature covers only three fields, so an extra field
would be unsigned content riding along.

### 4.1 File-drop transport

The file-drop transport carries HEAD_COMMITs and receipts through directories.
The node side is ILAS core's `FileDropWitness` (`src/s4/file-drop-witness.ts`).
It is a transport client: it retains nothing and is not a witness. The witness
side described here is the reference witness in `packages/witness`. The
directories are the wire, not the store. The evidence is the witness's own
store.

```
<intakeDir>/<submitterId>                         one file per node: the node renames its commit onto it, the witness reads and deletes it
<intakeDir>/.<submitterId>.<12 hex>.tmp           the node's temporary file while it writes a commit (a dot name, so the witness ignores it)
<that node's outboxDir>/receipt-<12 digits>.json  receipts: the witness writes them, that node reads them
<that node's outboxDir>/.staging/                 the witness's temporary files (a directory, so the node skips it)
```

`<intakeDir>` is either the node's own intake directory or one intake shared by
several nodes (see "One intake per submitter" below).

**Node configuration** (`FileDropWitness`):

| Field | Meaning |
|---|---|
| `id` | The witness set id. Written into every HEAD_COMMIT as `witness_set_id`. Must equal the witness's `witnessSetId`. |
| `intakeDir` | Where the commit file is written: this node's own intake, or the shared one. Never read back. The node needs permission to create, rename and remove entries in it. |
| `outboxDir` | This node's own outbox. Read, never written. |
| `submitterId` | The commit file's name, so it must be a name the file system holds exactly as spelled and the witness does not ignore: a non-empty string; not `.` or `..`; no `/` or `\`; no control character (U+0000–U+001F, U+007F–U+009F); well-formed Unicode (no lone surrogate, which would be written to disk as U+FFFD); not starting with `.`; at most 237 bytes in UTF-8 (the temporary name `.<submitterId>.<12 hex>.tmp` adds 18 bytes, and a file name holds at most 255). Otherwise the constructor throws `submitterId <problem>, got <the id as JSON>`. The rule is exported from `src/s4` as `submitterIdProblem()` and `MAX_SUBMITTER_ID_BYTES`; the reference witness refuses the same ids in its config. |
| `publicKeyPath` | Path of the witness's Ed25519 **public** key, as a PEM file. Optional in the type; without it no receipt is returned. A file that holds a private key is refused (see Retrieving). |

**Submitting.** `submit()` creates `intakeDir` if it is missing. It writes
exactly `JSON.stringify(commit) + "\n"` (the four HEAD_COMMIT keys, no
envelope) to a new file `<intakeDir>/.<submitterId>.<12 random hex>.tmp`,
created exclusively and without following a symbolic link
(`O_WRONLY|O_CREAT|O_EXCL|O_NOFOLLOW`: an existing file or symlink at that name
makes the write fail). It checks on the open descriptor that the file is a
regular file, writes and `fsync`s it through that descriptor, closes it, and
renames it onto `<intakeDir>/<submitterId>`. The rename replaces whatever
stands at that name (a regular file, a symlink, a hard link, a FIFO) without
following or opening it, so a planted link cannot redirect the write and a
planted FIFO cannot block the node, and the witness never sees a half-written
commit from this client.
The intake directory itself is not `fsync`ed. The new commit **replaces** any
commit already there: a commit that is replaced before the witness reads it is
never witnessed; the later commit covers a longer prefix of the chain. The
client never reads the intake back. A failed write (for example a directory at
the target name) is counted in `getSubmitDiagnostics()` and not thrown, and the
temporary file is removed. The name cannot vary with `seq_no`, because the
reference witness uses the whole file name as the submitter id.

Other accounts may be able to write the intake: the witness, and, with a
shared intake, the other nodes. Whatever stands at `<submitterId>` between two
submits may therefore have been planted; the client replaces it rather than
writing through it.

**Retrieving.** `retrieveReceipts()` lists `outboxDir` in name order. An entry
the listing reports as a directory (such as the witness's `.staging`) is
skipped unopened and not counted. Every other entry is opened once, by name,
with `O_RDONLY|O_NOFOLLOW|O_NONBLOCK`, and judged only on that descriptor, so
a symbolic link is never followed and a FIFO cannot block the node. If it is
not a regular file when opened, or is larger than 4096 bytes
(`MAX_RECEIPT_BYTES`), it is dropped unread. Nothing is checked by name and
then opened by name, so a writer of the outbox that renames something onto a
name in the meantime changes nothing. The file name is not interpreted: every
entry that is not a directory is opened. Each must parse as JSON, have exactly
the four receipt keys with the right types (§4), and carry a `witness_sig` in
canonical base64 (§4) that verifies against the public key. The key is re-read
on every call and must be an Ed25519 public key; a file holding a private key
is refused with a reason saying to give the node only the witness's public key.
The key file is opened `O_RDONLY|O_NONBLOCK` (a symbolic link is followed: the
operator chooses this path, and may rotate the key through a link) and judged
on that descriptor: anything but a regular file of at most 64 KiB (a FIFO, a
device, a directory, a larger file) is not read and counts as no usable key
(`cannot read witness public key: … is not a regular file; not read`), so a
FIFO at `publicKeyPath` cannot block `status()`.
Any other entry is dropped, with a reason in `getLastFetchDiagnostics()`.

- **With a usable key**, every dropped entry is a **rejection**: a symbolic
  link (`a symbolic link; not followed, not read`), a FIFO or other special
  file (`not a regular file when opened`), a file over 4096 bytes, an
  unreadable entry, malformed JSON, a wrong shape, a non-canonical signature
  or a signature that does not verify. `retrievalIssues()` reports the count
  and the reasons, and continuity reads `REJECTED_RECEIPTS` (§6). That
  includes a file that is not a receipt at all (a note an operator left
  there), a link to a genuine receipt, and every receipt when the configured
  key is the wrong one.
- **Without a usable key** (none configured, unreadable, not a regular file of
  at most 64 KiB, not Ed25519, or a private key), or with an unreadable outbox,
  nothing is returned and nothing counts as rejected: continuity is
  `CANNOT_VERIFY_CONTINUITY`. `getLastFetchDiagnostics()` then says why
  (`keyAvailable: false` and a reason, or `outbox unreadable: …`). A wrong
  `publicKeyPath` is a rejection only when it holds a different valid public
  key; a private key or a missing file there gives no key, not a rejection.

**One outbox per submitter, never shared.** The receipt preimage names neither
the submitter nor the witness set (G2). A receipt in a shared outbox would
verify for any node that trusts the same key, and nothing in it says whose head
it was. Which outbox a receipt is in is the only thing that says whose it is.
The reference witness therefore refuses a config in which two submitters share
an outbox, an outbox is an intake directory, or any two of these directories
are nested (compared after resolving symlinks).

At every start the reference witness also checks each outbox against its
store, by file name:

- Every file named `receipt-<12 digits>.json` must be, byte for byte, the
  receipt of that store record, and the record must belong to that outbox's
  submitter. A receipt for a record beyond the end of the store, a receipt
  that differs, or one for another submitter's record makes the witness refuse
  to start.
- Each entry with a receipt's name is opened once,
  `O_RDONLY|O_NOFOLLOW|O_NONBLOCK`, and judged on that descriptor. If it is not
  a regular file (a symbolic link, even one to the right bytes; a FIFO; a
  directory) or is larger than 4096 bytes, the witness refuses to start
  (`OUTBOX_UNREADABLE`). It never follows it, blocks on it, takes it for a
  receipt or replaces it.
- A receipt missing from an outbox is written again from the store (Ed25519
  signatures are deterministic, so the bytes are the same). So is one removed
  between the listing and the read.
- A file with **any other name** is only reported (`FOREIGN_OUTBOX_FILE`) and
  left in place, and the witness starts. A `.staging` that is not a real
  directory (a symlink, a file) is reported the same way and is not followed
  or cleared; receipts are not staged through it, and if a missing receipt has
  to be restored through it the witness refuses to start
  (`OUTBOX_UNWRITABLE`). From a real `.staging` directory, only the witness's
  own leftover staging files (`receipt-<12 digits>.json.<hex>.tmp`) are
  removed.

The node's client opens every entry of its outbox that is not a directory,
whatever its name, so a file the start-up check only reported still reaches
the client. One that does not verify makes continuity `REJECTED_RECEIPTS`; a
validly signed receipt put there under another name (for example a copy of
another node's receipt, which the same key signed, G2) is returned to the
predicate like any other receipt. Nothing but the witness should be able to
write an outbox, and each outbox should sit in a parent directory no node can
write, so that no node can put a directory of its own in its place.

**One intake per submitter (recommended with more than one node).** At the
witness, a submitter is identified by the intake path its commit is read from
(G8). In the reference witness each entry of `submitters` may name its own
`intakeDir`. Such a submitter's commit is read only from
`<its intakeDir>/<id>`; its name in any other intake is reported `UNDECLARED`
and left alone. The top-level `intakeDir` is then needed only for submitters
without one; if it is set anyway it is still polled. The witness refuses a
config in which two submitters' own intakes are one directory, a submitter's
own intake is the shared intake, any intake equals or is nested with an outbox
or another intake, or the store or the private key lies inside an intake.
Each node's intake should be writable only by that node's account (and by the
witness, which deletes what it consumes), inside a parent directory no node can
write.

**What the reference witness does with each intake entry.** Each poll lists
every intake directory (the shared one, if configured, and each submitter's
own) in name order. For each entry, the rows below are tried from top to
bottom; the first that fits applies.

| Entry | What the witness does | Event |
|---|---|---|
| Name starts with `.` | Ignores it: never reads, reports, moves or deletes it. These are the client's temporary files. | none |
| Name is not a submitter declared for this directory (in the shared intake, the name of a submitter that has its own intake counts as not declared) | Leaves it alone: never reads, moves or deletes it | `UNDECLARED` |
| Declared name, but a directory, symlink or other non-regular file | Does not follow or read it | `NOT_A_FILE` |
| Declared file larger than 4096 bytes | Does not read it | `REFUSED` |
| **Malformed:** not valid JSON | Leaves it and reads it again on the next poll: a writer that writes in place may have been caught half-way (the ILAS client renames into place, so this never happens with it). If the same bytes are still there, reports it. Never signs it. | `DEFERRED`, then `MALFORMED` |
| Valid JSON, but not an acceptable HEAD_COMMIT | Does not retain or sign it; leaves it | `REFUSED` |
| **Duplicate:** this submitter's `seq_no` and `head_hash` already retained, at any earlier point | No new record, no new receipt; deletes the intake file | `DUPLICATE` |
| **Conflicting:** same submitter, same `seq_no`, different `head_hash` | Retains and signs it. The store record carries a `SAME_SEQ_DIFFERENT_HEAD` note naming the earlier record. | `RETAINED` |
| **Rollback:** `seq_no` lower than the highest already retained for this submitter, with a head not retained before | Retains and signs it, with a `SEQ_LOWER_THAN_RETAINED` note | `RETAINED` |
| Anything else | Retains and signs it | `RETAINED` |

A declared entry is opened once, `O_RDONLY|O_NOFOLLOW|O_NONBLOCK`, and judged
and read only through that descriptor, never more than 4097 bytes of it: a
symbolic link is not followed, and a FIFO cannot block the poll. An undeclared
or dot-named entry is never opened.

An acceptable HEAD_COMMIT has exactly the keys `seq_no`, `head_hash`, `ts` and
`witness_set_id`; `seq_no` is a safe integer ≥ −1; `head_hash` is 64 lowercase
hex characters; `ts` is a finite number; `witness_set_id` equals the witness's
configured set; and −1 goes with the genesis hash and the genesis hash only
with −1 (§3). The node's `ts` is not part of what counts as a duplicate, so a
cadence re-emit of an unchanged head gets no second receipt.

Conflicting commits, and rollbacks to a head not retained before, are retained,
never dropped. The node then holds receipts that its live chain cannot all
reproduce, and §6 reports `MISMATCH`. A return to a head the witness already
retained for that submitter (exactly an earlier `seq_no` and `head_hash`) is a
**duplicate**: no record and no note are written, and the witness's store does
not show when the node went back. The rollback stays detectable: the node
holds the receipts for the higher heads the witness retained after that one,
its rolled-back chain cannot reproduce them, and §6 reports `MISMATCH`.

**Retaining, in order.**

1. Sign the receipt.
2. Hash the store record and sign it whole (`record_sig`, below), then append
   it to the witness's store (`O_APPEND`, then `fsync`).
3. Write the receipt to a new file
   `<outboxDir>/.staging/<name>.<12 random hex>.tmp`, created exclusively and
   without following a symbolic link (`O_CREAT|O_EXCL|O_NOFOLLOW`) and checked
   with `fstat` to be a regular file; `fsync` it, rename it to
   `<outboxDir>/<name>`, and `fsync` the outbox directory where the platform
   allows. `.staging` is created with mode 0700 and used only if `lstat` shows
   a real directory; otherwise the receipt stays pending (`RECEIPT_PENDING`).
   The node never sees a partial receipt.
4. Re-read the intake file and delete it only if its bytes are unchanged.
   Otherwise it is left for the next poll (`INTAKE_LEFT`).

A commit the node writes between that re-read and the delete is deleted
unprocessed; the next cadence commit replaces it. If the receipt write fails,
the record stays retained, the intake file is still consumed, and the write is
retried on every poll (`RECEIPT_PENDING`, then `RECEIPT_WRITTEN`). If the store
append fails, the witness halts, says why on stderr, and stays halted until it
is restarted.

**The witness's store.** One JSON line per retained commit, with the keys
`index`, `prev_hash`, `submitter_id`, `commit`, `witness_ts`, `witness_sig`,
`conflicts`, `hash` and `record_sig`, in that order. `hash` is the SHA-256 of
the canonical form (§7.2) of the first seven; `prev_hash` is the previous
record's `hash` (64 zeros for the first). `record_sig` is the base64 Ed25519
signature, by the witness key, over the UTF-8 string
`"ILAS-WITNESS-STORE-RECORD-1\n" + hash`. Because `hash` covers `prev_hash`,
each `record_sig` vouches for its record whole and for the store up to it:
without the key, nobody can change a field, re-attribute a record to another
submitter, renumber, reorder, or remove or replay a record, even with every
hash recomputed. At start-up and in `verify`, the witness refuses a record
without `record_sig` or with one that does not verify; a store written by a
version of the witness that did not sign records therefore no longer verifies.
A store cut back to a clean prefix still verifies (G3); the outbox check above
notices that only while an outbox still holds the later receipts.

**Receipt files.** Named `receipt-<store index, zero-padded to 12
digits>.json`, for example `receipt-000000000000.json`. The content is the
receipt of §4 as one JSON object, keys in the order `seq_no`, `head_hash`,
`witness_ts`, `witness_sig`, followed by a newline. Names sort in store order.
The index counts across all submitters, so the numbering in one outbox has
gaps. Whatever already stands at a receipt's name is never overwritten: a file
with different bytes, or anything that is not a regular file (a symbolic link,
even one to the right bytes; a FIFO; a directory). The receipt then stays
`RECEIPT_PENDING`.

## 5. Hash chain (L0 entries)

Each entry's hash:

```
hash = sha256( JSON.stringify({
  sequenceNumber, previousHash, timestamp, moduleId, eventType,
  provenanceTag, parameters, outcome, clerkReceipt
}) )
```

Genesis `previousHash` is 64 zeros. Key order in the JSON is the order above.
`verify()` recomputes every hash and every link from genesis, and requires each
entry's stored `sequenceNumber` to equal its position in the chain. It reports
the first index where any of these fails. It never throws: an entry whose hash
cannot be recomputed (nested too deeply for the stack) fails at its index.

`verify()` proves internal consistency only. A truncated prefix verifies. A full
rewrite with recomputed hashes also verifies. Detecting either needs an external
anchor (§6).

**What an entry holds (the payload snapshot).** When `append()` is called, L0
reads exactly six fields of the input, once: `timestamp`, `moduleId`,
`eventType`, `provenanceTag`, `parameters` and `outcome`. Any other key on the
input is ignored. It normalises them with a JSON round trip,
`JSON.parse(JSON.stringify(picked))`, so the result is exactly what a JSON line
on disk would hold: `NaN` and `±Infinity` become `null`, properties whose value
is `undefined` are dropped, `undefined` array elements become `null`, and a
`toJSON` method is applied. That snapshot is frozen, and it is the only thing
used afterwards: it is what is hashed and stored, and with a clerk route it is
the payload submitted to the clerk, its `timestamp` is the
`declared_timestamp`, and it is what `payload_commitment` is checked against
(§7.3). Nothing is read from the caller's object after `append()` returns, so
changing that object later changes nothing on the log. For ordinary JSON data
the snapshot equals the input, and its hash is the same as before.

An input that has no JSON form (a `BigInt`, a cycle, a `toJSON` that throws,
whatever it throws), or that is nested too deeply for the stack to freeze,
hash or serialise, is refused with `L0PayloadError` before anything is
submitted or committed (`entry is nested too deeply to be kept; nothing was
submitted or committed: …`, or `entry cannot be hashed or serialised (nested
too deeply); nothing was committed: …`), never with a raw `RangeError`. With a
clerk route, three more are refused the same way:

- a snapshot that has no canonical form (§7.2; nesting deeper than 64
  levels), since its receipt could never verify;
- a snapshot whose `timestamp` is neither a number nor `null` (a string, an
  object, or missing; `NaN` and `±Infinity` have already become `null`),
  since that is all a clerk books as `declared_timestamp`;
- a snapshot whose canonical form is larger, in UTF-8 bytes, than the clerk
  client's `maxPayloadBytes` (below).

Without a clerk the error is thrown from `append()`; with a clerk the append's
promise rejects. A refused payload refuses that one append only; it does not
stop the log (§7.6).

**Payload size limit.** A clerk client may declare
`readonly maxPayloadBytes?: number` on its `ClerkSubmitClient`: the largest
payload it can deliver, counted in UTF-8 bytes of the snapshot's canonical
form (§7.2). L0 reads it once, when the log is built. If it is present, it
must be a positive safe integer, or the constructor throws `L0ClerkError`
(§7.3). A larger entry is refused with `L0PayloadError` (`entry is <n> bytes
in canonical form; the clerk client takes at most <limit>; nothing was
submitted or committed`) before it is submitted: nothing is booked or
committed, the log goes on, and the next entry that fits is submitted as
usual. A client that declares no limit gets none from L0. The reference
clerk's `SocketClerkClient` declares 1045414 bytes, the most that always fits
on one request line (§7.5); its `InProcessClerkClient` declares none.

**Entries are immutable.** Every committed entry, and every entry loaded from
disk, is deep-frozen, including `parameters` and `clerkReceipt`: what
`getEntry()`, `getAll()` and `append()` hand out cannot be changed (an
assignment throws `TypeError` in strict mode). `getAll()` returns a frozen copy
of the chain, not a live view: an array handed out earlier does not show later
appends, and sorting, reversing or splicing it throws `TypeError` without
reaching the chain.

**Opening a durable log.** A relative path is anchored first, once, at
construction: the working directory of that moment is put in front of it
(prefixed, not normalised, so `..`, a symbolic link or a trailing slash is
left for the file system to resolve as it would the path as given). The log,
its lock and the checks before each append all use that absolute path, so a
later `process.chdir()` changes nothing. `getDurabilityInfo().path` still
reports the path as given. If the working directory cannot be read at
construction (it was removed), the load is `CANNOT_VERIFY` with `lastError`
`cannot resolve the relative log path <path>: the working directory cannot be
read (…)`, no lock is taken, and the constructor does not throw.

With a path, L0 then takes the writer lock (One writer per file, below), and
opens the file **once**, by name, with
`O_RDWR|O_APPEND|O_NOFOLLOW|O_NONBLOCK`. Everything after that is done on that
descriptor: the read at load and every append. What the open finds decides
the start:

- **The open fails with `ENOENT`: the file is absent** (`FIRST_BOOT_OR_ERASED`).
  L0 creates the file's directory if it is missing and creates the file at
  once, at construction, with an exclusive create (mode 0666 less the umask);
  with `fsync` on (below) it also syncs the directory, where the platform
  allows. If the directory or the file cannot be created (for example because
  the parent is not writable), the state stays `FIRST_BOOT_OR_ERASED`,
  `persisting` and `writeHealthy` are false, and every append is refused with
  `L0WriteError`; with a clerk route, before anything is submitted (§7.6).
- **The open fails with `EACCES`, `EPERM` or `EROFS`.** L0 tries a read-only
  open (`O_RDONLY|O_NOFOLLOW|O_NONBLOCK`). If that works, the history is
  loaded and checked as below and can be `LOADED_VERIFIED`, but `persisting`
  and `writeHealthy` are false, `lastError` reads `log file is not writable:
  …`, and every append is refused with `L0WriteError` (with a clerk route,
  before anything is submitted). Permissions are judged at the open: a file
  made read-only while a log runs is still written through the descriptor
  that log holds, and the next start loads it read-only.
- **Any other failure means history may be there and cannot be reached:**
  `EACCES` on a directory above it, `ENOTDIR` (a path through a regular file,
  or a trailing slash after an existing file), `EISDIR`, `EIO`, `ENXIO` (a
  socket at the path), and `ELOOP`: a symbolic link **at** the log path is
  never followed. The load is `CANNOT_VERIFY` with nothing loaded, and
  `lastError` reads `cannot read log file: <error>` (for a link, followed by
  `(a symbolic link at the log path is not followed)`).
- **The descriptor is not a regular file** (`fstat`: a FIFO, a device):
  `CANNOT_VERIFY`, `lastError` `cannot read log file: <path> is not a regular
  file (a FIFO)`. A directory at the path is refused by the open itself
  (`EISDIR`). The open never blocks, so a FIFO at the log
  path cannot stop the node.

**Loading.** The file is read through the descriptor in pieces of 1 MiB and
split into lines at each `\n` byte; each line is decoded on its own. The
whole file is never one string, so a log longer than the longest string the
runtime can make still loads; only each single line must fit in one. The
whole chain is still kept in memory, so the memory available to the process
bounds the size of a log that can be loaded.

Line *i* holds entry *i*, and every line, a blank one included, must be:

- a JSON object whose keys are all among `sequenceNumber`, `hash`,
  `previousHash`, `timestamp`, `moduleId`, `eventType`, `provenanceTag`,
  `parameters`, `outcome` and `clerkReceipt`;
- stored exactly as L0 writes it: its bytes equal the UTF-8 bytes of
  `JSON.stringify(JSON.parse(line))`. A repeated key (which `JSON.parse`
  would resolve silently to its last value, text the hash never covered),
  extra whitespace, another escape for the same character, a CRLF ending, or
  bytes that are not UTF-8 all fail this;

then `verify()` must pass; then, with a clerk route, every entry's receipt
must pass §7.3. The first line that fails stops the load, and nothing after it
is read. A line that is not JSON (`malformed JSON at line <i>: …`; a blank
line too), not an object or has another key (`line <i> is not a log entry:
…`), is not stored as L0 writes it (`line <i> is not stored as L0 writes it:
it is not exactly JSON.stringify of its own entry (a repeated key, extra
whitespace, another escape, or bytes that are not UTF-8)`), or cannot be
loaded (`line <i> cannot be loaded: …`, for example nesting too deep to
freeze) makes the load `CANNOT_VERIFY` at that line with nothing loaded; a
failed `verify()` or receipt check makes it `CANNOT_VERIFY` at that index,
with the entries kept in memory for inspection. Any other fault while loading
also gives `CANNOT_VERIFY`, with `lastError` `log file could not be loaded:
…`. The load itself never throws (the writer lock can make the constructor
throw; below). An empty file loads as `FIRST_BOOT_OR_ERASED` and is written
onward.

**The end of the file.** A file that does not end with a newline is not
repaired by deleting anything:

- If its last line parses as an entry (and the chain verifies, and with a
  clerk route its receipts check), the file loads `LOADED_VERIFIED`, and the
  next entry is written after a single `"\n"`, so it never joins that line.
- If its last line does not parse (that includes a last line of whitespace
  only), the load is `CANNOT_VERIFY`, `brokenAt` is that line's index, and
  `lastError` reads `torn final line at index <i>: the file ends inside this
  line, without a newline; nothing was removed`. L0 never truncates history at
  load. A line that does not parse followed by a newline is still `malformed
  JSON at line <i>`.

**After a `CANNOT_VERIFY` load.** A `CANNOT_VERIFY` log never writes to the
file in that process. `ILASKillStack` still makes its construction-time
appends on such a log; they live in memory only, after any loaded entries, and
with a clerk route they are still submitted, so the clerk books receipts for
entries that never reach the file (G7). Head commits sent from such a node
describe that memory-only chain; the witness retains them, and no later start
can reproduce them. The state comes back on **every** start: a restart does
not clear it, and the node keeps running with its entries in memory only until
someone acts. The way back keeps the evidence:

1. Stop every process that runs on the log. Never edit, truncate or delete the
   file. Record `brokenAt`, `lastError`, `entriesLoaded`, and the file's size
   and SHA-256.
2. Move the file aside unchanged (or point `logPath` at a new file), and keep
   it as evidence. The next start on the new file is `FIRST_BOOT_OR_ERASED`
   once, then `LOADED_VERIFIED`.
3. If the node is witnessed, give it a fresh witness submitter: a new
   submitter id, with its own new intake and outbox, at the witness. The
   witness keeps every head it retained for the old submitter id, and a new
   log starts a new chain from genesis, so under the old id those receipts
   read `MISMATCH` against the new log for as long as the witness's store
   exists (§4.1; the outbox is rebuilt from the store at every start).
4. With a clerk route, the same clerk and key can serve the new log. The book
   keeps the receipts of the old log and of the memory-only entries; `clerk
   reconcile` lists them (G7).

The same applies whenever a node starts a new log file for another reason:
enabling a clerk route on a log begun without one, or changing the clerk key
(§7.3).

**Writing.** An entry is serialised as one JSON line and written through the
descriptor with `writeSync`, in a loop until every byte is written, then
`fsync`ed; only then is it committed to the in-memory chain. The option
`fsync` (`LockedEvidenceLogOptions.fsync`, passed through by
`ILASKillStackOptions.fsync`) is `true` by default; `false` is meant only for
tests and benchmarks that ask for it, and then an entry is on disk only once
the operating system flushes it, so an operating-system crash or a power loss
can take entries a witness or a clerk already holds. With `fsync` on, a crash
of the process or of the operating system, or a power loss, keeps every entry
that was committed, on storage that honours `fsync`. The cost is one `fsync`
per entry.

Before each write L0 checks that the path still names the file it opened (the
same device and inode) at the size it left it. If the file was removed
(`the log file <path> was removed while this log ran`), replaced (`… is no
longer the file this log opened (replaced while it ran)`) or written by
someone else (`the log file is <n> bytes; this log left it at <m>, so
something else wrote to it`), nothing is written, the append throws
`L0WriteError`, and the log writes nothing more. It never re-creates the file.

A write or `fsync` that fails may have landed part of the line, so L0 cuts the
file back to its size before the entry (`ftruncate` on the descriptor, then
`fsync`):

- If that works, the append throws `L0WriteError` (`… the file was cut back to
  the <n> bytes it held before this entry, and the entry was not committed`)
  and `writeHealthy` is false. Without a clerk route a later append may try
  again; with one, the failure stops the log (§7.6).
- If the cut-back fails too, `lastError` ends `… so the file may hold a torn
  line. This log writes nothing more`, and this and every later append throws
  `L0WriteError` (with a clerk route, before anything is submitted). Memory
  never runs ahead of disk. The next start reports the torn line as above.

**One writer per file.** Two writers appending to one file would fork its
chain, and the next start could not load it. Before it reads the file, a
durable log takes a writer lock, `<path>.lock` (mode 0644), that holds one
JSON line:

```
{"pid":<pid>,"instance":<32 hex characters>,"processStart":"<proc:… or uptime:…>","started":<ISO 8601 time>}
```

`processStart` says when the locking process started. On Linux it is `proc:`
followed by field 22 of `/proc/self/stat` (the process's start time in clock
ticks after boot); elsewhere, or without `/proc`, it is `uptime:` followed by
`Date.now() - process.uptime()` in whole seconds, and two `uptime:` values
within 2 s of each other count as the same start.

Where the file system has hard links, the lock appears whole or not at all.
Its text is written (and, with `fsync` on, synced) to a staged file beside
it, `.ilas-lock-<instance>` in the log's
directory, created exclusively without following a symbolic link; the staged
file is then hard-linked to `<path>.lock`, which fails if a lock is already
there, and removed. A crash can therefore leave a stray `.ilas-lock-<32 hex>`
file, which is harmless and may be deleted, but never an empty or half-written
lock. On a file system without hard links (`link()` fails with `EPERM`,
`ENOTSUP`, `EOPNOTSUPP`, `ENOSYS` or `EXDEV`) the lock is created in place with
an exclusive create and then written, as before; there a crash between the
two can still leave an empty lock, which the next start refuses (below).

- **Another live process holds the lock:** the constructor of
  `LockedEvidenceLog`, and so `new ILASKillStack()` and
  `ILASKillStack.create()`, throws `L0WriteError`: `the log <path> is in use
  by process <pid> (writer lock <path>.lock). Two writers on one log file fork
  its chain. If no node is running on this log (the pid may now belong to
  another program), remove the lock file by hand.` Two writers are a
  deployment error, and fail at start-up. This is the one case in which
  `LockedEvidenceLog`'s constructor throws because of its path.
- **Another thread of this process holds the lock** (a worker thread): the
  lock names this pid and this `processStart`, with an instance this thread
  did not create. The constructor throws `L0WriteError` the same way: `the log
  <path> is in use by another thread of this process (pid <pid>, writer lock
  <path>.lock). Two writers on one log file fork its chain. If no thread of
  this process writes this log (a worker that ended without close()), remove
  the lock file by hand.` A worker that ends without `close()` (for example
  through `terminate()`) leaves its lock, and every other thread of the
  process refuses the log until the lock is removed by hand or the process
  ends.
- **A lock that cannot be parsed is refused, never taken over:** an empty or
  damaged file, one not written by L0, or one whose `processStart` is present
  but malformed. The constructor throws `L0WriteError`: `the writer lock
  <path>.lock names no process: it cannot be parsed as a writer lock (empty,
  damaged, or not written by L0), so it is not taken over. Check that no
  process has <path> open (for example: lsof <path>, or fuser <path>), then
  remove <path>.lock by hand.` Something at the lock path that cannot be read
  at all (a symbolic link, which is not followed; not a regular file; larger
  than 4096 bytes; no permission) throws `the writer lock <path>.lock cannot
  be read (…). If no node is running on <path>, remove it by hand.`
- **A stale lock is taken over:** one whose pid is no longer running, or one
  that names this pid with **another** `processStart`, or with none (an
  earlier process with the same pid, such as a container restarted as pid 1;
  a lock written before `processStart` was recorded counts the same).
  `getDurabilityInfo().lockTakenOver` is then `true`. After a crash or a
  `SIGKILL` that is expected. Two processes that take over the same stale lock
  at the same moment have a small window; the next start's verification
  reports a fork.
- Pids are compared within one pid namespace: the lock does not keep apart
  writers in different containers, or on different hosts, that share one log
  file. One storage path, one writer, remains a deployment property (§2).
- **A lock that cannot be created** (a directory that is not writable or not
  searchable): the load still runs. A load that would write instead refuses
  writes: `persisting` and `writeHealthy` false, `lastError` `cannot create
  the writer lock <path>.lock: …` (or `cannot write the writer lock …` when
  its text could not be written; the staged file is then removed), and every
  append throws `L0WriteError`. A `CANNOT_VERIFY` load keeps its own
  `lastError`.
- **Within one thread the newest `LockedEvidenceLog` on a path owns it.**
  Opening another one on the same path supersedes the older one: it closes its
  file, and every append on it throws `L0WriteError` (`append write failed at
  seq <n>: superseded: a newer LockedEvidenceLog on <path> in this process
  owns the file`), with a clerk route before anything is submitted. Another
  thread opening the same path is refused instead (above).
- **`close()`** (`LockedEvidenceLog.close()`, `ILASKillStack.close()`) stops
  writing, closes the file and releases the lock. Later appends throw
  `L0WriteError` (`… closed: this log was closed`). Calling it twice is
  harmless. Await `settle()` (or `settleEvidence()`) first: an append still
  waiting for its receipt is refused when it reaches the file. The lock is
  also removed when the process exits normally (Node's `exit` event), but not
  after `SIGKILL` or an unhandled `SIGTERM` or `SIGINT`; the next start then
  takes the stale lock over. `ILASKillStack.close()` first stops V0's
  deprecated staleness timer (`clearStalenessTimeout()`), so a closed stack
  never moves its state, or appends, on a timer.
- **An append made from a timer never throws out of it.** If V0's staleness
  timer is still armed on a log that has been closed or superseded or cannot
  write (for example when a newer stack opened the same path), the append it
  makes fails: V0's state still moves, but its log entry does not land. That
  failure is kept, through
  `LockedEvidenceLog.keepFailure(err)`, under the same rule as a failure an
  `enqueue()` met (§7.6), and the next `settle()` (`settleEvidence()`) throws
  it. It never becomes an uncaught exception. `keepFailure()` itself never
  throws, whatever it is given.
- An in-memory log (no path) takes no lock, and `close()` leaves it working.
- A durable log that writes keeps one file descriptor open for its life, and
  the newest log on each path is held until `close()` or exit, so code that
  opens logs on many paths should close them.

## 6. Continuity predicate

`ContinuityVerifier` takes the receipts the `Witness` returns and checks every
one of them against the live chain, never only the latest. It does not check
their signatures; the `Witness` implementation does (§2). The heads for all
receipts are recomputed in one pass from genesis over the entries' contents,
trusting no stored hash, so the cost grows with the chain plus the receipts:

- **`seq_no` ≥ 0.** Compare `head_hash` with the recomputed head at that
  sequence. If the chain has no entry at that sequence (it is shorter than the
  witness's evidence), or the recomputed head differs from `head_hash`, the
  receipt does not reproduce.
- **`seq_no` = −1.** The head of the empty prefix (§3). The receipt reproduces
  exactly when `head_hash` is the genesis hash (64 zeros), on any chain. Seq −1
  with any other hash does not reproduce.
- **`seq_no` < −1.** Names no prefix of any chain. Does not reproduce.
- **`seq_no` not a safe integer** (`NaN`, `1.5`, `Infinity`, a string). Names
  no prefix. Does not reproduce.
- **An entry up to `seq_no` cannot be hashed** (nested too deeply for the
  stack). The head cannot be recomputed, so the receipt does not reproduce:
  `recomputed_head_hash` is `null` and the reason reads `the head at seq <n>
  cannot be recomputed: an entry up to it cannot be hashed`. Recomputing heads
  never throws.

A `Witness` may also implement the optional `retrievalIssues()`, which returns
`{ rejected, reasons }` for its most recent `retrieveReceipts()` call:
`rejected` counts the receipts it was able to check (it had what it needs to
verify them) and refused. `FileDropWitness` implements it (§4.1). A `Witness`
without it is read as rejecting nothing.

A `Witness` may also implement the optional `publicKeyFingerprint(): string |
null`: the fingerprint (§2.1) of the public key it checks receipts against, or
`null` without a usable key. `FileDropWitness` implements it, re-reading the
key with the same checks as a fetch (§4.1); `NullWitness` does not.
`status().declarations.keys.witness` carries it (`null` for a `Witness`
without the method). It names the key the node trusts, so the witness's
operator can compare it with what their `keygen` printed.

The status is the first of these that applies:

| Status | Meaning |
|---|---|
| `MISMATCH` | At least one returned receipt does not reproduce. A hard finding. Each one is listed with its reason. |
| `REJECTED_RECEIPTS` | The `Witness` refused receipts it was able to check: forged, corrupted, malformed, or signed by another key. A hard finding: something in the witness channel does not verify. It is reported even when every returned receipt reproduced. |
| `CANNOT_VERIFY_CONTINUITY` | No receipts to check: no witness, no key, nothing retained yet, or an unreadable outbox. Says nothing about continuity. |
| `VERIFIED_HISTORICAL` | Every receipt the `Witness` verified and returned reproduces from the live chain, and none was refused. Upgrades nothing. |

`VERIFIED_HISTORICAL` cannot see a receipt that is no longer there: if genuine
receipts are deleted from the outbox (nothing forged), the ones that remain can
still reproduce. Only the reference witness's start-up check, which writes
missing receipts again from its store (§4.1), brings such a deletion back into
view.

`ContinuityVerifier.verify()`, and `ILASKillStack.verifyContinuity()`, return
the whole report: `status`, `receiptsChecked`, `mismatches` (each with
`seq_no`, `expected_head_hash`, `recomputed_head_hash` and `reason`),
`rejectedReceipts`, `rejectReasons` and `ts`. A `MISMATCH` report still carries
any rejections. `ILASKillStack.status().continuity` carries only the status.

Clean results are never converted into integrity upgrades for the v0 state.

## 7. Clerk receipt, verification, and known gaps

### 7.1 Clerk submission receipt

Carried on each L0 entry as `clerkReceipt`. It is a flat record. Every field
except `receipt_hash` and `signature` is covered by the signature. There is no
fixed field list in the verifier: whatever the clerk puts in the record is
signed. L0 keeps the whole record it was handed on the entry, inside the
entry's hash (§5).

The fields L0 reads are typed as `ClerkSubmissionReceipt` in `src/types.ts`,
including `submitter_id` and `channel`, which must name the route (§7.3). The
reference clerk writes all of them plus `receipt_form`
(`"ILAS-CLERK-RECEIPT-1"`) (`packages/clerk/README.md` §2).

L0 copies a receipt through JSON (`JSON.parse(JSON.stringify(receipt))`)
before it checks it, and stores that copy, frozen. What is checked is exactly
what is stored.

### 7.2 Canonical form (`ILAS-CANON-JSON-1`)

Canonical bytes of a JSON-shaped value:

- object keys sorted by UTF-16 code unit (as JavaScript's default sort does);
  no whitespace;
- object keys and string values use JSON string escaping (as
  `JSON.stringify` writes them); numbers use JSON number form;
- every property is read exactly once;
- object properties whose value is `undefined` are omitted;
- an `undefined` array element is **refused**, not coerced to `null`;
- non-finite numbers, bigint, functions, symbols, and cycles are **refused**;
  an object reached twice without a cycle (a shared reference) is encoded each
  time;
- a `toJSON` method, if present, is called exactly once and its result encoded;
- depth is bounded: the root value is at depth 0, and each member of an object
  or array at depth *d* is at depth *d* + 1. A value at depth greater than 64
  is refused.

Examples (from the vectors):

```
{"b":1,"a":2}          → {"a":2,"b":1}
{"a":1,"gone":undefined} → {"a":1}
```

### 7.3 Clerk verification rule (closes G1)

A clerk receipt is accepted only if all three hold:

1. `receipt_hash` = SHA-256 of `preimage`, where
   `preimage = canonical(record minus receipt_hash and signature)`.
2. `signature` is a valid Ed25519 signature, made by the **configured clerk
   key**, over the UTF-8 bytes of `preimage`, in canonical base64: exactly the
   text `Buffer.from(s, "base64").toString("base64")` gives back, so 88
   characters with `==` padding. Any other spelling of the same bytes is
   refused (`signature is not canonical base64`).
3. `payload_commitment` = SHA-256 of `canonical(payload)`, where `payload` is the
   exact object L0 submitted for this entry: the entry's six-field snapshot
   (§5). This binds the receipt to one entry. A valid receipt for a different
   payload is refused.

`signature_alg` must be `"ed25519"`. The clerk key must be configured explicitly
(`clerkPublicKeyPem` on the route). There is no default.

**Bound to the route, and used once.** The receipt must also name the route it
came back on: `submitter_id` must equal the route's `submitterId`, and
`channel` must equal the route's `channel`. A receipt booked for another
submitter or channel is not a receipt for this log. And a receipt commits at
most once per log: a receipt whose `receipt_hash` is already on an entry of the
chain (including entries loaded from disk) is refused with
`clerk receipt is already committed on this log (receipt_hash …); a receipt
binds one entry; L0 append did not land`. A clerk that hands back the same
receipt for two identical entries, or a receipt replayed after a restart, is
therefore refused. `clerk_seq` order along the log is not checked (G7).

**Checked at construction.** The clerk route is validated and copied when
`LockedEvidenceLog` is constructed, and so when `ILASKillStack` is. The
constructor throws `L0ClerkError` if the client has no `submit()` method; if
the client's `maxPayloadBytes` is present but not a positive safe integer
(§5); if `submitterId` or `channel` is not a non-empty string; or if
`clerkPublicKeyPem` is missing, empty, a private key, cannot be read as a
public key, or is not an Ed25519 key. A private key is PEM text containing
`PRIVATE KEY`, or anything Node parses as a private key; the error says
`clerkPublicKeyPem holds a private key. Give the node only the clerk's public
key (clerk.pub.pem); the private key stays with the clerk.` (`verifyClerkReceipt`
refuses a private key too.) A wiring mistake therefore fails at start-up, not
at the first append. `clerkPublicKeyPem` is the PEM text, not a path: a key
file that cannot be read fails in the caller's own file read, before ILAS sees
it. Each of the route's four fields is read exactly once, and so is the
client's `maxPayloadBytes`: the values that were checked are the values kept,
whatever accessors the route object has. A route whose field cannot be read (a
getter throws) gives `L0ClerkError` `clerk route could not be read: …`. The
route is copied and frozen, so changing the caller's route object later cannot
swap the key under a running log.

**Shape checks.** Before the cryptographic check, L0 refuses a receipt that is
not an object (`clerk returned no receipt object`), and a receipt unless:
`kind` is `"SUBMISSION"`; `clerk_seq` is an integer ≥ 0; `clerk_time.wall_ms`
is a finite number and `clerk_time.monotonic_ns` a non-empty string;
`declared_timestamp` equals the entry's `timestamp`; `receipt_hash` is a
non-empty string; `signature_alg` is `"ed25519"`; `separation` is
`SEPARATE_PROCESS` or `IN_PROCESS_NO_SEPARATION`; `intake` is `SOCKET`,
`LOCAL_CALL` or `CLERK_INTERNAL`; the receipt does not claim
`SEPARATE_PROCESS` together with `LOCAL_CALL`; and `submitter_id` and
`channel` name the route.

Failures are refused, and nothing is committed. Each refusal names its rule:
a shape refusal reads `clerk returned a malformed or mismatched receipt
(<rule>); L0 append did not land`, for example `(channel does not name this
route's channel)`; a cryptographic one reads `clerk receipt failed verification
(<reason>)`, for example `receipt_hash does not match the canonical record`,
`signature does not verify against the configured clerk key` or
`payload_commitment does not match the submitted payload`. A receipt that
cannot even be read (a throwing getter) gives `clerk receipt could not be
checked`. Every refusal is a clerk failure and stops the log (§7.6).

**Checked again on load.** With a durable log and a clerk route, the hash chain
alone is not enough: anyone who can write the file can recompute hashes. So
after `verify()` passes on a non-empty file, every loaded entry must carry a
receipt that passes the same rule as an append: the shape checks (including
`declared_timestamp` equal to the entry's `timestamp`), the route binding, a
`receipt_hash` not used earlier in the file, and the signature by the route's
key with `payload_commitment` over the entry's own stored six fields. The first
entry without a receipt, or with one that fails, makes the load
`CANNOT_VERIFY`: not clean, not persisting, `brokenAt` that index, and
`lastError` `clerk receipt check failed at index <i>: <reason>`. The entries
stay in memory for inspection. Under a clerk route, `LOADED_VERIFIED`
therefore means every receipt on the log was checked. Without a clerk route,
loading checks the hash chain only: receipts on the loaded entries are
whatever the file holds, and anyone who can write the file can recompute the
hashes. `getDurabilityInfo().receiptsUnchecked` (and
`status().logDurability.receiptsUnchecked`) counts the loaded entries that
carry a clerk receipt although the log was loaded without a route, so nothing
checked them. It is fixed at load, and 0 with a route or in memory.
`clean` still describes only the hash chain (and, with a route, the receipts
that route checked): a log can be `clean` with `receiptsUnchecked` above 0. A
node that declares a clerk and reports `receiptsUnchecked` above 0 is a
finding.

Two consequences for operators:

- **A log started without a clerk is `CANNOT_VERIFY` when opened with one**
  (its entries carry no receipts). Start a new log file when enabling a clerk.
- **Changing the clerk key** makes every receipt signed with the old key fail
  on reload, so the log loads `CANNOT_VERIFY`. There is no list of earlier
  keys. Start a new log file with the new key.

Interoperability: receipts from the reference clerk (`packages/clerk`) verify
under this rule. Its tests check that with ILAS's own `verifyClerkReceipt`,
against a running clerkd and against the published clerk vector (§8), and that
ILAS refuses its receipts when they name another submitter or channel.

### 7.4 Known gaps (open)

- **G1 — closed (§7.3).** The clerk signature is now verified against the
  configured key, and the receipt is bound to its payload.
- **G1b — clerk identity is key-based.** A valid receipt proves the configured
  key signed it. It does not prove which process held the key, or that the key
  was not shared. Key custody is a deployer obligation.
- **G2 — no domain separation in the witness preimage.** The witness preimage
  does not name the witness set or the submitter. A key used for two witness
  sets could sign receipts valid in both, and a receipt signed for one node
  verifies for any node that trusts the same key. The reference witness keeps
  receipts apart by layout, one outbox per submitter (§4.1), not by
  cryptography. The fix is a versioned preimage that adds a set identifier,
  which changes the vectors.
- **G3 — the witness receipts are retained only by the witness.** ILAS keeps no
  WORM copy. A witness that deletes history removes the anchor. Retention is a
  deployer obligation. The reference witness signs every store record (§4.1),
  so without its key a record cannot be changed, re-attributed, reordered or
  removed from the middle; a store cut back to a clean prefix still verifies.
  On the node, receipts deleted from the outbox leave no trace in the client:
  the remaining ones can still read `VERIFIED_HISTORICAL` (§6), and only the
  witness's start-up check writes them back.
- **G4 — shared directories are not a witness.** The file-drop client talks to a
  witness through directories (§4.1). A witness that reads and writes the same
  directory as the node is not independent, however it is named.
- **G5 — the time base is not checked.** `witness_ts` and `clerk_time` are
  recorded, not validated against anything.
- **G6 — submitters are not authenticated.** A clerk could require each
  submitter to prove that it holds a registered key, for example by signing a
  challenge, before booking its request. Neither ILAS nor the reference clerk
  does this. The reference clerk's `allowed_submitters` list is a name check:
  anyone who can connect to its socket can present any name on the list. Who
  can connect is limited only by the socket's permissions (§7.5). L0 refuses a
  receipt that names another submitter or channel than its route (§7.3); that
  keeps another submitter's receipts off this log, but says nothing about who
  sent the request. The witness side of the same gap is G8.
- **G7 — a clerk's book can hold receipts the node never committed.** The clerk
  books a receipt before the node checks it. If the node refuses the receipt
  (§7.3, for example because it is configured with a different clerk key), if
  the answer is lost, if the client times out after sending, if the append
  was already in flight when an earlier one failed (§7.6), or if writing the
  confirmed entry to the durable log fails after the clerk booked its receipt
  (`L0WriteError`, §7.6), the book holds a receipt that is on no entry of the
  node's log. The same holds for entries committed in memory only, on a log
  that loaded `CANNOT_VERIFY` (§5). Along the log this shows as missing
  `clerk_seq` values. ILAS does not flag gaps in `clerk_seq`, because
  receipts may legitimately be interleaved (one clerk can serve several
  submitters, which share its numbering) or reordered (a client that sends
  requests concurrently can have them numbered in a different order than L0
  commits them). L0 does guarantee that every receipt on its log names this
  node's `submitter_id` and `channel` and that no `receipt_hash` appears on the
  log twice (§7.3). The clerk `fsync`s a receipt before it answers, and L0
  writes the entry only after that, so a power loss between the two also
  leaves a booked receipt with no log entry.

  The gap is checkable with the reference clerk's `reconcile` command
  (`packages/clerk/README.md` §6):

  ```
  npx ts-node packages/clerk/src/cli.ts reconcile --book <book.jsonl> --log <l0.jsonl> [--log <l0.jsonl> ...] --pub <clerk.pub.pem> --submitter <id> --channel <ch>
  ```

  It verifies the book first (a book that does not verify is an error and
  nothing is compared), then reads each log as data: it takes no writer lock,
  writes nothing, and does not check the hash chain, which L0 does at load. It
  reads lines more loosely than L0's load (§5): it skips blank lines and does
  not require each line to be exactly as L0 writes it, so it can read a log
  that L0 refuses to load. Every receipt on a log is checked with ILAS's own
  receipt rules for its entry, imported from ILAS core: `verifyClerkReceipt`
  (§7.3) with the clerk's key and the entry's six payload fields, a
  `submitter_id` and `channel` that name the reconciled route, and each
  receipt on at most one entry of a log (within one log file, as L0 checks;
  the same receipt in two `--log` files is not flagged). It does not apply
  L0's key-less shape checks of §7.3 (a `declared_timestamp` equal to the
  entry's `timestamp`; known `kind`, `separation` and `intake`). It lists:

  - (a) receipts booked for that submitter and channel that no log entry
    carries, by `clerk_seq` and `receipt_hash`; an entry whose receipt is in
    (c) does not count as carrying it;
  - (b) log entries whose receipt passes those rules but is not in the book
    (`not in the book`);
  - (c) log entries whose receipt fails those rules (L0 refuses such a log
    under this route), with the reason: `submitter_id "…" does not name the
    reconciled submitter`, `channel "…" does not name the reconciled
    channel`, `the same receipt as entry <n> of this log; a receipt binds one
    entry`, `fails ILAS's receipt check: <reason>` (for example
    `payload_commitment does not match the submitted payload` or `signature
    does not verify against the configured clerk key`), or `clerkReceipt is
    not a JSON object`.

  Log entries without a receipt are counted and not compared. Exit 0: no
  gaps; 3: any of (a), (b) or (c) is not empty; 1: an error (a book that does
  not verify, a log with a torn or malformed line, a file that is not a
  regular file); 2: usage. `--log` may repeat, for a node whose earlier log
  files were moved aside (§5); the receipts of a log passed that way are
  matched, and those of a log left out are listed in (a). Every entry of (a),
  (b) and (c) needs an explanation; a log that `reconcile` refuses cannot be
  compared, and its receipts show up in (a).
- **G8 — at the witness, a submitter is identified by the intake path it writes
  to; not authenticated.** The reference witness attributes a commit to the
  submitter whose intake path it was read from, `<intakeDir>/<id>`, and cannot
  check who wrote the file. With one shared intake, any node that can write it
  can submit under any declared name: the witness retains and signs that commit
  for the named node, and that node's untouched chain then reads `MISMATCH` (a
  false alarm that stays as long as the witness's store does). The receipt
  preimage does not name the submitter either (G2). The mitigation is
  deployment, not cryptography: give each node its own intake directory
  (§4.1), writable only by that node's account and the witness, inside a parent
  directory no node can write.
- **G9 — anyone who can connect to the clerk socket can hold its connections.**
  The reference clerk serves at most 64 connections at once and closes one only
  when it is idle for 30 s or a request line is not complete within 10 s of its
  first byte (§7.5). A peer that sends complete lines, even empty ones, more
  often than every 30 s keeps its connections. With all 64 held, submissions
  fail, and every node that submits meanwhile stops its L0 until it is
  restarted (§7.6). The daemon cannot tell peers apart, so it cannot limit them
  one by one. With `socket_mode` `"0600"` only the clerk's own account can do
  this; with `"0660"`, every member of the socket's group can. A peer that
  sends requests and reads the answers slowly, or never, can still hold its
  connection, but it can no longer make clerkd queue answers in memory; and no
  peer, however fast it pipelines requests and reads answers, can keep clerkd
  from serving the others or from accepting new connections: connections are
  served one request per turn, round-robin (fairness and backpressure, §7.5).
- **G10 — no transport between machines.** The reference clerk speaks only
  over a Unix domain socket, so it runs on the node's host; a separate account
  there is supported, another machine is not. A forwarded socket (for example
  over SSH) would be a transport the deployer provides and secures; none is
  included or tested. The file-drop witness transport is directories: a
  witness on another machine needs a directory both machines reach, shared or
  synced, which the deployer provides, together with their own analysis of who
  can write each intake and each outbox on it (G4, G8). Remote transports are
  out of scope for this repository.

### 7.5 Clerk socket transport (reference clerk)

This is the transport `packages/clerk` implements. L0 itself only calls
`ClerkSubmitClient.submit()`; any client that returns a receipt meeting §7.3
will do.

**Framing.** A Unix domain socket carrying newline-delimited JSON (`\n`). The
daemon answers every request line with exactly one response line, in order, on
the same connection, also when the peer has already ended its side of the
connection (Half-close, below).

**Request.**

```
{"submitter_id": "node-a", "channel": "l0", "declared_timestamp": 1700000000007, "payload": {...}}
```

- Exactly these four keys. An unknown key is refused.
- `submitter_id` and `channel`: non-empty strings of at most 256 characters
  (UTF-16 code units).
- `declared_timestamp`: a finite number or `null`. An absent value is treated
  as `null`.
- `payload`: required; any JSON value.
- The line must be valid UTF-8 and valid JSON, and at most 1 MiB (1 048 576
  bytes) long, not counting the newline. A payload of at most 1 045 414 bytes
  in canonical form always fits, whatever names and timestamp come with it
  (Client, below).

L0 sends its route's `submitterId` and `channel`, the snapshot's `timestamp` as
`declared_timestamp`, and the entry's six-field snapshot as `payload`
(`timestamp`, `moduleId`, `eventType`, `provenanceTag`, `parameters` and
`outcome`, JSON-normalised; §5).

**Response.**

```
{"ok": true, "receipt": {...}}
{"ok": false, "error": "<reason>"}
```

A receipt is returned only after it has been appended to the clerk's book and
`fsync`ed. `"ok": false` means no receipt was returned: either the request was
refused before anything was booked (malformed request, unknown key, a name not
on `allowed_submitters`, a payload without a canonical form), or the clerk has
stopped after a failed book write and refuses every request until it is
restarted. A request line over the limit is answered with
`{"ok":false,"error":"request line longer than 1048576 bytes; connection closed"}`,
and the connection is closed.

**Daemon limits.** A request line must be complete within 10 s of its first
byte. The clock starts at a line's first byte and stops at its newline; later
bytes do not restart it, and it runs again for each line, so a long-lived
connection whose lines each arrive in time is unaffected. A line still
incomplete at the deadline is answered with
`{"ok":false,"error":"request line not complete within 10000 ms of its first byte; connection closed"}`,
and the connection is closed. Idle connections are closed after 30 s. At most
64 connections at once (what these limits do not stop: G9).

**Fairness.** Connections take turns. clerkd serves one request per turn,
round-robin over the connections that hold a complete request line, in the
order they became ready, and each turn runs in its own pass of the event
loop, so new data and new connections are read between any two requests. A
connection with more complete lines waiting goes to the back of the queue
after its turn. A peer that pipelines requests, even one that reads every
answer at once, is therefore served one request per round like every other
connection, and cannot keep clerkd from serving the others or from accepting
new connections.

**Backpressure.** Each connection has at most one answer in flight: once it
has sent a complete line, clerkd reads nothing more from it until that line
has had its turn and the answer has left the process. A client may pipeline
requests, but it must read its answers to be served further. A peer that
never reads stops being served once the socket's buffers are full (about 300
receipts with Linux defaults), and is closed when it has been idle for 30 s.
A connection whose unsent output passes `MAX_UNSENT_BYTES` (8 MiB, the most
any client reads as one answer) is closed at once. A client that writes a
large batch and starts reading only after the whole write has completed can
therefore stall until the idle timeout; `SocketClerkClient` sends one line and
then reads, and is unaffected.

**Half-close.** A peer may end its side of the connection right after its
last request. clerkd still answers every complete line the peer sent before
it ended, in order, and only then ends its own side; ending early does not
cost a peer the answers to receipts already booked for it. A last line
without its newline gets no answer.

The socket path may
be at most 107 bytes on Linux (103 elsewhere), and its directory must leave
room for the 9-byte temporary name clerkd binds first (below); otherwise
clerkd refuses to start and says why.

**Readiness probe (`clerk ping`).** `ping --socket <path> [--timeout-ms N]`
(`pingClerkd()` in `packages/clerk/src/client.ts`) opens one connection and
sends one probe line, `{}` (`PING_PROBE`). clerkd always refuses it (it names
no submitter), so nothing is booked, and answers it like any request. The
probe succeeds once a well-formed clerkd response line arrives within the
timeout (default 5000 ms; N must be a whole number from 1 to 2147483647):
`{"ok":true,"receipt":{…}}`, or `{"ok":false,"error":"<string>"}`. It fails
when nothing listens on the path (a missing file; a socket file left behind
by a clerkd that was killed, `ECONNREFUSED`), when the answer does not arrive
in time, when the peer closes without answering, and when the answer is not
such a line. A clerkd that has stopped after a failed book write still answers,
and answers EVERY line, the probe included, with `clerk stopped: <reason>`
before validating it; `ping` then prints the reason and exits 4, so a stopped
clerk never passes the probe. A probe that succeeds (exit 0) shows that
clerkd is listening and has not stopped. The
example service unit in `docs/INSTALL-FOR-AGENTS.md` (step 8) counts clerkd as
started only once this probe succeeds.

**Socket permissions.**

- `socket_mode` `"0600"` (the default): only the clerk's own account can
  connect. `"0660"`: the socket's group can connect too.
- clerkd does not bind the socket path directly. It binds a temporary name (a
  dot and 8 hex characters) in the socket's directory, sets the mode on it,
  hard-links it to the socket path, and removes the temporary name. If
  something appears at the socket path in the meantime, clerkd refuses to
  start rather than replace it. The socket's file system must allow hard links
  to sockets.
- The socket's directory is created with mode 0700 if it does not exist. On
  start it is checked: with `"0600"` it must give group and other users no
  access; with `"0660"` it must give other users no access. Otherwise clerkd
  refuses to start.
- A regular file at the socket path is never removed. A socket another process
  is listening on is never taken over. A socket left by a dead process is
  removed. On SIGINT or SIGTERM clerkd removes its socket, only if the socket
  path is still the one it linked (the same inode), so stopping one clerkd never
  removes a socket another clerkd has since put there; and it removes its lock
  file.
- The signal must reach clerkd's own node process. Start it with
  `node node_modules/ts-node/dist/bin.js packages/clerk/src/cli.ts run --config <file>`
  (or exec that command from a supervisor), not with `npx`: npx runs its
  command under `sh -c`, and where `/bin/sh` is dash a SIGTERM to the npx
  process stops npx and the shell and leaves clerkd running, with its socket
  and book lock. clerkd prints its pid in its `clerkd: listening on …` line;
  that is the process to signal (`packages/clerk/README.md` §6).
- Started through npm or npx anyway (`npm_command` is `exec`, or
  `npm_lifecycle_event` is set), `run` prints one warning line on stderr at
  start: signals sent to npx (or npm) may not reach clerkd, followed by its pid
  and the direct command, with every path in it absolute: this process's node
  binary (`process.execPath`), ts-node's `dist/bin.js`, the `cli.ts` in use
  and the config file, quoted for the shell where needed. That command works
  as printed from any directory. clerkd then runs as usual; it never stops
  itself over how it was launched. The reference witness's `run` does the same
  (`packages/witness/README.md`, Command line).

**Client (`SocketClerkClient`).** One connection per request, and one request
in flight per client, so a client's requests reach the clerk in the order
`submit()` was called. Before connecting it refuses a payload that would not
reach the clerk unchanged (its canonical form changes across a JSON round
trip, or it has none: `ClerkPayloadError`) and a request line over 1 MiB
(`ClerkRequestError`). It reads at most 8 MiB of response. It waits 10 s by
default for the connection and the answer; `timeoutMs` must be more than 0 and
at most 2147483647 ms (about 24.8 days, the longest delay a Node timer keeps),
or the constructor throws. It does not check the signature;
L0 does (§7.3). Every error it raises reaches the caller of `append()` as
`L0ClerkError`, and stops the log (§7.6).

The client declares `maxPayloadBytes` = 1 045 414 (`MAX_PAYLOAD_BYTES` in
`packages/clerk/src/wire.ts`), so L0 refuses a larger entry with
`L0PayloadError` before submitting it (§5), and a request line that would be
too long never reaches the clerk. The figure is the line limit minus the most
a line can hold besides its payload:

```
{"submitter_id":S,"channel":C,"declared_timestamp":T,"payload":P}

fixed text      16 + 11 + 22 + 11 + 1                          61
S and C         2 x (2 quotes + 256 code units x 6 bytes)     3076
T               a JSON number, e.g. -0.0000012345678901234567   25
everything but P                                              3162
P               the payload's canonical bytes (JSON writes the same bytes)
maxPayloadBytes 1048576 - 3162                             1045414
```

Six bytes is the most JSON spends on one UTF-16 code unit (a control character
or a lone surrogate, written `\uXXXX`). `InProcessClerkClient` sends nothing
over a wire and declares no limit.

**`separation` and `intake`.** These are fixed when the clerk is opened, not
measured. The daemon cannot see which process is at the other end of its
socket.

| Clerk | `separation` | `intake` | `separation_warning` |
|---|---|---|---|
| Daemon (clerkd, `SocketClerkClient`) | `SEPARATE_PROCESS` | `SOCKET` | `null` |
| In-process (`InProcessClerkClient`) | `IN_PROCESS_NO_SEPARATION` | `LOCAL_CALL` | A sentence saying the in-process clerk buys no separation |

L0 also accepts `intake: "CLERK_INTERNAL"` (§7.3). The reference clerk does
not write it.

### 7.6 Fail closed after a clerk failure

With a clerk route, the first append that fails stops the log for the life of
the process. A failure is any of these: the client's `submit()` throws or its
promise rejects (clerk down, refusal, timeout); the clerk returns something
that is not a receipt object, or a receipt that cannot be read; the receipt
fails a shape check, the route binding, the at-most-once rule or the rule in
§7.3; or, with a durable log, writing the confirmed entry fails
(`L0WriteError`, even when the file could be cut back, §5), or the log refuses
writes (`L0WriteError`, at the next append, before it is submitted): the log
file was absent and its directory or the file could not be created, the file
is not writable by this process, the writer lock could not be created, an
earlier failed write could not be taken back, the file was removed, replaced
or written by someone else, or the log was superseded or closed (§5).

A refused payload is **not** a failure in this sense: an entry with no JSON or
canonical form, a timestamp that is neither a number nor `null`, or a
canonical form larger than the client's `maxPayloadBytes` (§5) is refused with
`L0PayloadError` before anything is submitted. That entry alone is refused;
the log goes on, and the next entry is submitted as usual.

When the stop takes effect:

- A `submit()` that **throws** stops further submissions at once.
- A submission whose promise **rejects** stops further submissions as soon as
  L0 observes the rejection, at the latest one microtask after it settles.
  L0 watches every submission from the moment it is made.
- A receipt refusal or a failed write is found when that append's turn to
  commit comes (appends commit in the order they were called), and stops
  further submissions from then on.
- A log that refuses writes from construction (a directory or file that could
  not be created, a file that is not writable, a writer lock that could not be
  created) is known before anything is submitted. The first append is refused
  with `L0WriteError` before it is submitted, and stops the log, so nothing is
  ever submitted: `ILASKillStack.create()` rejects without the clerk booking
  any construction-time entry. A refusal that arises while the log runs (a
  write that could not be taken back, a file changed under it, a newer log on
  the path, `close()`) stops it the same way at the next append.

From then on:

- Every later `append()` is refused with the recorded error **before** anything
  is submitted, so the clerk never books a frame the log has already decided
  not to commit.
- Nothing called after the failing append commits. Appends called after it but
  submitted before the stop took effect are refused when their turn to commit
  comes; the clerk may already have booked them (G7). In particular, if a
  client returns a promise that is already rejected, appends issued in the same
  synchronous run, before L0 has observed the rejection, are still submitted.
- Appends called **before** the failing one keep their place in commit order,
  and still commit if their own receipts verify.
- Callers that use `enqueue()` see the error at `settle()`,
  `ILASKillStack.ready()` or `settleEvidence()`. An error that stopped the log
  is thrown by every later `settle()`; a refused payload is thrown by the next
  `settle()` only, and never hides or replaces an error that stopped the log.
  A failure kept with `keepFailure()` (an append from V0's staleness timer,
  §5) follows the same rule.
- A clerk failure never becomes an unhandled promise rejection, whatever the
  client throws or rejects with, an `Error` or not (an object with no string
  form, one whose `toString` throws, a revoked `Proxy`, a `Symbol`). A failed
  submission is reported as `L0ClerkError`, with the original value kept as
  its `cause`; where that value has no string form, the message reads
  `[object Object]` or `[unprintable value]`. With a clerk route `append()`
  never throws synchronously. A failure surfaces only through the promises of
  `append()`, `settle()`, `ready()`, `settleEvidence()` and
  `ILASKillStack.create()`.

Recovery is a restart (fail closed), once the cause is gone (for a clerk that
was down, start the clerk first). There is no method to clear the state. A
restart recovers a stopped clerk route; it does **not** clear a `CANNOT_VERIFY`
load, which comes back on every start until the log file is replaced (§5,
After a `CANNOT_VERIFY` load).
With a durable log, the restart loads and re-verifies the file, every clerk
receipt included (§7.3), before accepting it. On a restart that loads
`LOADED_VERIFIED`, `ILASKillStack` appends only those construction-time entries
the loaded chain does not already hold (matched by `moduleId`, `eventType`,
`provenanceTag`, `parameters` and `outcome`, the timestamp ignored; each loaded
entry matches at most one), so a start-up that a clerk failure cut short is
completed on the next start, and a complete one adds nothing. `status()` has no
field for the stopped state; the failure surfaces through the rejected appends
and `settle()`.

Without a clerk route this section does not apply. A failed durable write
throws `L0WriteError` from that `append()` (synchronously) and commits nothing;
when the file could be cut back (§5) that refuses this append only, and a
later one may try again; memory never runs ahead of disk. A log that refuses
writes (§5: a directory or file that cannot be created, a file that is not
writable, a writer lock that cannot be created, a write that could not be
taken back, a file changed under it, superseded, closed) throws `L0WriteError`
from every append. When the refusal is known at construction and the stack
has construction-time entries to write (a first boot), `new ILASKillStack({
logPath })` throws at start-up; a verified log that loads read-only starts,
because the entries it already holds are not written again, and its first
new append throws. (With a clerk route the same refusal is
a failure under this section: the first append rejects with `L0WriteError`
before anything is submitted, the log stops, and `ILASKillStack.create()`
rejects.) Another live process holding the writer lock makes the constructor
itself throw `L0WriteError`, with or without a clerk route (§5). A log path
that cannot be read for any other reason (a path through a regular file, a
directory without search permission, a FIFO, a symbolic link) is not this
case: the load is `CANNOT_VERIFY` (§5), the node starts, and its appends live
in memory only.

## 8. Reproducing the vectors

```
npx ts-node scripts/s4-test-vectors.ts
git diff --exit-code docs/s4-test-vectors.json
```

No diff means this checkout reproduces the vectors. A diff means either the code
or the vectors changed, and the change must be reviewed before anything is
committed. `git diff` only compares against a committed file: where the vector
file is not committed, compare its md5 before and after the generator runs.

ILAS core checks every section of the file with its own code, in the ordinary
test run: the hash chain from the generator's entries, every canonical example,
both witness receipts (and that `receipt_valid` names this chain's head at
seq 3), and both clerk receipts, including that `clerk_receipt_valid` commits
through an L0 route bound to `vector-submitter` / `vector-channel`:

```
npx ts-node src/vectors.test.ts
```

The reference packages check the same file with their own code:

```
npx ts-node packages/witness/src/vectors.test.ts
npx ts-node packages/clerk/src/vectors.test.ts
```

- The witness test uses the package's own preimage and verifier, nothing from
  ILAS core. It checks that `receipt_valid` verifies and `receipt_altered_seq`
  does not, that the `0x42` seed gives the published witness key and
  signature, and that the witness core, given that seed and a fixed clock,
  writes exactly `receipt_valid`.
- The clerk test checks `clerk_receipt_valid` and
  `clerk_receipt_wrong_payload` with the package's own verifier and with ILAS's
  `verifyClerkReceipt`, checks that the `0x43` seed reproduces the published
  `receipt_hash` and `signature`, and runs `cli verify` on the vector as a
  one-receipt book.

`npm test` runs all three, with every other test file.
